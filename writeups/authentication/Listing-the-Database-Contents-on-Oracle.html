SQL Injection | Practitioner

Lab Description

This lab contains an SQL injection vulnerability in the product category filter. The results from the query are returned in the application's response, allowing a UNION attack to retrieve data from other tables. Since the application database uses randomized table and column configurations on an Oracle infrastructure, we must map out the system schema before we can extract credentials.

Goal: Enumerate the Oracle database structure to locate the randomized user credentials table, extract its dynamic columns, and log in as the administrator user.

Mindset & Strategy

When mapping database architecture on an Oracle backend, we cannot use information_schema because Oracle does not support it. Instead, Oracle uses its own specific metadata views to track objects.

Our strategy relies on two main Oracle data dictionary views:

°      all_tables: To retrieve a list of all tables accessible to our database session.

°      all_tab_columns: To retrieve a list of all columns mapped to our target table.

Remember that Oracle strictly requires a FROM clause for all queries. We must also ensure that table names passed into metadata filters are completely capitalized because Oracle handles identifiers as uppercase strings by default.

Step-By-Step-Execution

1. Determine Column Configuration: Access the lab and click on any category filter. Perform column and type verification using:
/filter?category=' UNION SELECT 'a','a' FROM dual--
The application returns an HTTP 200 OK without errors, confirming that the backend query returns exactly **two columns**, and both are fully compatible with string data types.

2. Enumerate Table Structure: Query Oracle's global table tracking index to look up available user tables. Remember to append the required FROM statement pointing to all_tables:

/filter?category=' UNION SELECT NULL,table_name FROM all_tables--

Analyze the returned list. Scroll down past the default Oracle system tables until you spot a highly interesting, randomized user table signature: USERS_JSLKCH.

3. Enumerate Column Mapping: To discover the randomized column definitions within our newly discovered table, query the metadata view all_tab_columns. Ensure you filter the search using the exact uppercase table name:

/filter?category=' UNION SELECT NULL,column_name FROM all_tab_columns WHERE table_name='USERS_JSLKCH'--

4. Identify Target Fields: Examine the UI layout output rows. You will identify three specific custom column markers containing core details: EMAIL, USERNAME_TEQXXU, and PASSWORD_WSFNXH.

5. Exfiltrate Sensitive Credentials: Now that both the table name and column keys are fully mapped, modify the placeholders to target these specific values directly:

/filter?category=' UNION SELECT PASSWORD_WSFNXH,USERNAME_TEQXXU FROM USERS_JSLKCH--

6. Log in and Complete: Read through the printed response content lines. Locate the row profile corresponding to the administrator user and extract the plain-text password. Navigate to "My account" in the menu bar, log in with these credentials, and the lab will instantly mark itself as solved.

Technical Explanation

The backend core takes input arguments and builds an unvalidated execution block:

SELECT item, description FROM products WHERE category = '' UNION SELECT PASSWORD_WSFNXH, USERNAME_TEQXXU FROM USERS_JSLKCH--'

In an Oracle architecture environment, system objects are registered in system catalog views. By invoking a UNION selection loop over all_tables and all_tab_columns, an attacker can trace database schemas step-by-step. Because Oracle stores metadata table arguments using uppercase text strings by default, passing table_name='USERS_JSLKCH' in strict uppercase ensures our filter clause returns a match, allowing us to successfully exfiltrate the administrative credentials dataset.

How To Fix

°      Deploy Strongly Parameterized Queries: Ensure all incoming user parameter inputs are bound cleanly via prepared statement engines, preventing raw input strings from altering query structure.

°      Restrict Catalog Views Access: Implement strict database permissions to restrict access to system catalogs. Make sure the application database user account cannot read data dictionary tables like all_tables or all_tab_columns.

°      Enforce Input Field Sanitization: Implement server-side verification filters using rigid alphanumeric character validation schemas to inspect and discard payloads containing relational operator structures or trailing SQL comment sequences like --.
