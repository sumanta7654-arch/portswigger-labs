SQL Injection | Practitioner

Lab Description

This lab contains an SQL injection vulnerability in the product category filter. The query results are rendered directly in the application's response, making it vulnerable to a UNION attack. To capture credentials, we must first discover the schema layout because the database utilizes randomized table and column configurations.

Goal: Enumerate the database tracking architecture using metadata tables, isolate the randomized user credentials table, extract the columns, and log in as the administrator.

Mindset & Strategy

In real-world penetration testing, table names are rarely as simple as users or columns as predictable as username and password. When application builders scramble identifiers, we must look for a standardized metadata registry.

On non-Oracle relational database management systems (RDBMS) like PostgreSQL, MySQL, and Microsoft SQL Server, this structural directory is known as the Information Schema. Our strategy is to query information_schema.tables to find the custom user storage tables, then query information_schema.columns to retrieve the randomized field names, and finally execute a precision UNION attack to exfiltrate the administrative secrets.

Step-By-Step-Execution

1. Map Basic Dimensions: Access the application and click on any category filter. Perform standard structural reconnaissance using ' UNION SELECT NULL,NULL--. The application resolves with an HTTP 200 OK statement, confirming the target framework returns exactly two columns, and structural validation verifies both support string injections.

2. Enumerate Table Schemas: Since we need to look up table configurations, query the global metadata views. To filter out noise and internal system definitions, specify the scope context using the public table schema constraint parameter:

/filter?category=' UNION SELECT NULL,table_name FROM information_schema.tables WHERE table_schema='public'--

Examine the printed list rows to isolate the unique user dictionary signature name; in this tracking iteration, it reveals itself as users_tdzuuv.

3. Enumerate Columns: Now that we hold the table identifier token, query the column directory view to find out exactly how the individual tracking arrays are named. Filter the database scope explicitly matching your discovered user table string:

/filter?category=' UNION SELECT NULL,column_name FROM information_schema.columns WHERE table_name='users_tdzuuv'--

Analyze the returned results. The page structure outputs three matching columns inside the targeted map scope: email, username_esxoqq, and password_fnmwit.

4. Exfiltrate Targeted Data: With the exact mapping keys for both table and columns discovered, replace your placeholder selectors with these specific fields to extract the raw credentials stream directly from storage:

/filter?category=' UNION SELECT username_esxoqq,password_fnmwit FROM users_tdzuuv--

5. Authenticate and Complete: Read through the printed response content rows in your browser viewport. Locate the administrator row entry profile and copy its corresponding string hash. Navigate to "My account," insert the admin user ID along with the extracted string token, and submit to mark the lab module tracking solved.

Technical Explanation

Most relational database engines feature a standardized set of read-only views collectively referred to as the Information Schema. Whenever user operations input unstructured inputs into raw statement blocks, it permits attackers to dynamically extract the database's own structural dictionary mapping data.

By filtering structural query layouts against the table_schema='public' context variable, we can filter out complex engine configurations and narrow our scope down to user-created elements. Since our structural verification checks proved that both columns accept text data types, we can skip string formatting tricks and extract the target parameters simultaneously across the single unified output block layout loop.

How To Fix

°      Enforce Parameterization: Stop constructing SQL strings dynamically through string concatenation or interpolation models. Mandate prepared queries with strongly-bound data objects to prevent user strings from shifting the underlying relational structures.

°      Restrict Metadata System Privileges: Tighten backend service database operational rules. Ensure the application session's account profile does not hold global read permissions over systemic meta directories such as information_schema.tables or information_schema.columns.

°      Leverage Application Layer Object Abstraction: Utilize secure Object-Relational Mapping (ORM) tools that manage state interaction pipelines securely. This ensures that parameter structures are checked and safely isolated at runtime before executing calls against database entities.
