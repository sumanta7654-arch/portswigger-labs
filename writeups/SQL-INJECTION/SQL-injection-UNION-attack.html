SQL Injection | Practitioner

Lab Description

This lab contains an SQL injection vulnerability in the product category filter. The results from the query are returned in the application's response, making it vulnerable to a UNION attack. However, before executing a full data exfiltration exploit, we must find out how many columns the original query returns.

Goal: Determine the exact number of columns returned by the query by injecting a series of UNION SELECT payloads containing NULL values.

Mindset & Strategy

When executing an SQL injection UNION attack, there are two strict technical requirements enforced by the database engine:

°      The injected UNION SELECT statement must return the exact same number of columns as the original query.

°      The data types of the columns must be compatible across both queries.

Our strategy is to systematically test the column structure by passing arrays of NULL values. We use NULL because it is accepted as a valid placeholder for almost any data type (strings, integers, booleans), which helps us isolate the column count without triggering data-type errors prematurely.

Step-By-Step-Execution

1. Locate the Injection Vector: Access the lab home page. To find a parameter interacting with the database, click on any filter category (e.g., Pets or Accessories). Observe the URL structure changes to: /filter?category=Pets.

2. Test with Two Columns: Clear the original category value from the URL and inject two null placeholders:
/filter?category=' UNION SELECT NULL,NULL--
Send the request. The server returns an HTTP 500 Internal Server Error, proving the column count does not equal 2.

3. Test with Three Columns: Increment the count by adding a third null placeholder to the parameter:
/filter?category=' UNION SELECT NULL,NULL,NULL--

4. Analyze the Successful Response: Send the modified payload. The server processes the request cleanly, returning an HTTP 200 OK without any structural errors. This confirms the backend table query handles exactly three columns.

5. Verify Success: Because your payload perfectly matched the column structure, the web application successfully resolves the execution. The lab banner changes to solved.

Technical Explanation

When the query executes on the database backend, it resolves into a structure similar to this:

SELECT name, description, price FROM products WHERE category = '' UNION SELECT NULL, NULL, NULL--'

If the count of elements in our injected SELECT block differs from the initial query execution block, the database engine drops the query processing entirely and throws a fatal compilation error (resulting in the application's 500 Internal Error response). Once we match the exact column tally, the dataset joins cleanly. The trailing -- syntax forces the engine engine to truncate the rest of the application's native verification block.

How To Fix

°      Implement Parameterization: Use prepared statement routing frameworks to pass variables separately from structural statement strings, preventing the interpolation of user-supplied commands like UNION.

°      Object Relational Mapping (ORM): Abstract underlying relational architecture using modernized ORM structures (like Hibernate or Entity Framework) that isolate programmatic parameters safely.

°      Deploy Web Application Firewalls (WAF): Configure network inspection policies to actively identify and drop structural query parameters containing raw signature syntax variants like UNION SELECT.
